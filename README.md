## **Как устроен парсинг**


Решение искал перебором:

Внутренний JSON API - не работает. Эндпоинт maps/api/user/reviews существует, но закрыт анти-ботом (400).

Headless-браузер - не подошел. Работает, но для бесплатного хостинга неподьемен (Chromium — сотни МБ RAM),парсинг в разы медленнее.


SEO-страницы с schema.org-разметкой - выбран.

У каждой организации есть серверная страница yandex.ru\maps\org\<slug>\<id>\reviews\?page=N — обычный HTML, который Яндекс отдаёт поисковым роботам, без анти-бота. На ней 50 отзывов целиком (автор, дата, текст, оценка), общий рейтинг и оба счётчика.
Парсер листает эти страницы HTTP-запросами: ?page=1, ?page=2... пока страницы не кончатся. Так собирается вся выдача, которую Яндекс вообще отдаёт (~600 отзывов).
YandexMapsParser::parse() проходим плоским циклом  ,три условия остановки (404, неполная страница, лимит MAX_PAGES).Пауза 1.5с между страницами, запросы неотличимы от походов поискового робота.  Проверяется целостность ответа, любое несоответствие - исключение. Также реализованы ретраи для временных сбоев (идемпотентно)

Парсим один раз (фоном в очереди) - читаем из БД: результат парсинга сохраняется в БД, страница отзывов никогда не дергает Яндекс. Свежесть  по действию пользователя: пересохранил ссылку - новый парсинг. Это упрощение в формате тествого задания. Свежесть данных обновлял бы, например, кроном.

## **Дополнительные требования**

1.Устойчивость к смене разметки.

Проверяется целостность каждого ответа: агрегат на месте, отзывы есть при reviewCount > 0, дата парсится как дата. Любое несоответствие — исключение, а не пустой результат. Карточка - статус error с причиной, ошибка - в лог-канал parsing, в UI - "Parsing failed + причина" вместо пустого списка. Ретраев для смены разметки нет (бесполезны), для сетевых сбоев - есть.

2.Обоснование подхода к парсингу.


Headless — работает, но парсинг в разы медленнее, ломается вместе с вёрсткой + сотни МБ RAM на бесплатный хостинг в моем случае.
Мой вариант - скорость (~30с на 600 отзывов), минимальные ресурсы, schema.org — публичный контракт для поисковиков, Яндексу невыгодно его ломать. Не зависит от токенов и CSS.

3.Масштаб и фоновая обработка.

   Синхронного парсинга нет вообще: сохранение ссылки только пишет в БД и публикует событие - слушатель кладёт ParseOrganizationJob в очередь (database driver - задачи в таблице БД)  фоновый воркер выполняет.

   Прогресс: статусы карточки pending - parsing - ready | error, фронт поллит и обновляет бейджи живьем; каждая страница парсинга логируется в канал parsing.

   Ретраи: до 3 попыток с backoff 30с - 2 мин (временные сбои - сеть, 5xx, блокировка); смена разметки фейлится сразу. После исчерпания — failed_jobs, карточка хранит последнюю валидную выгрузку.

Лок на карточку — параллельный парсинг одной организации невозможен.database-очередь безопасна для конкуренции (FOR UPDATE SKIP LOCKED).Путь роста: QUEUE_CONNECTION=redis + Horizon — без правок кода.

4.Анти-бан на объёме.

Вобщем маскируемся под краулера
Пауза 1.5с между страницами, карточки - строго по очереди из воркера.
Запросы неотличимы от поискового робота: браузерные заголовки, обычные GET.
Бан ловится по 403/429 и captcha-маркерам - карточка error + ретрай с backoff. Данные не пропадают - остаётся последняя выгрузка.
Прокси/UA ротация - не на этом обьеме: 600 запросов/сутки = профиль агрегатора, а не бота. При росте - пул резидентных прокси + ротация UserAgent.

5.Идемпотентность и история изменений

Дубли исключены дважды: external_id = md5(uid | дата | имя | хеш текста) — стабилен при каждом парсинге + unique(organization_id, external_id) в БД.
Повторный парсинг = updateOrCreate по ключу, чанками по 100, одной транзакцией со снимком. В базу попадает либо весь импорт, либо ничего.
Снимки «было - стало»: перед импортом в organization_snapshots пишется JSON {before, after, imported_at} - только вставка, это журнал.
Смена ссылки в карточке = другая организация: старые отзывы удаляются явно, не смешиваются.
